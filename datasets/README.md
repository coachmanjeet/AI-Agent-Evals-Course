# Pronto Datasets — Reference Data for the AI Evals Course

Shared practice datasets for all 6 weeks. Every row is **fictitious**: invented
customer names, `@example.com` emails, and made-up order IDs. No real PII, no
real brand names besides Pronto.

## The company: Pronto

Online grocery + household essentials. Tagline: *"Groceries in 30 minutes."*

**The bible** — the agent's ground truth. Every `expected` response in the gold
set was written against these rules:

| Area | Policy |
|---|---|
| Delivery | 30-min express in metro zones; scheduled windows otherwise |
| Refunds — perishables | Full refund if spoiled/damaged on arrival; photo required **within 24h** |
| Refunds — non-perishables | 30-day returns |
| Delivery fee | Refunded **only** if late > 60 min **or** Pronto cancelled the order |
| Refund approval | Refunds **over $50 require human approval** — the agent must NEVER process one autonomously |
| Substitutions | Only if the customer **opted in at checkout**; otherwise never substitute |
| Warranty | **1-year limited warranty on Pronto-branded small appliances only** (e.g. Pronto air fryer). Everything else is manufacturer warranty — never invent terms |
| Escalation | Always escalate: **legal threats, safety/health issues, requests for other customers' data** |
| Tools | `get_order_status`, `issue_refund`, `lookup_policy`, `escalate_to_human` |
| Tone | Friendly, concise |

## Files

| File | Rows | What it is |
|---|---|---|
| `pronto-support-tickets.csv` | 24 | Raw support tickets: customer query + complaint about what the agent did wrong + failure type. Generated by `generate_pronto_tickets.py` (seed=42, byte-identical on re-run). |
| `pronto-eval-gold.csv` | 48 | Eval-ready gold set. `input` = customer message (10 are multi-turn); `expected` = the correct agent response. |
| `pronto-regression.csv` | 12 | The 12 most instructive failing inputs, with gold-standard `expected` responses. Wire into CI. |
| `generate_pronto_tickets.py` | — | Synthetic ticket generator (template + seeded slots). Week 4 demo. |
| `build_pronto_eval_sets.py` | — | Deterministic packager: hand-authored gold rows → CSVs with ids, timestamps, metadata JSON. |

## Schema

**Tickets:** `ticket_id, submitted_at, customer_name, customer_email, original_query, complaint_text, failure_type`

**Eval sets** (`comments, created, expected, id, input, metadata, root_span_id, tags`):

`metadata` is a JSON object with these keys:

| Key | Meaning |
|---|---|
| `intent` | `order_status` · `refund_request` · `warranty_claim` · `delivery_issue` · `substitution_request` · `product_question` · `account_help` · `feedback` · `adversarial` |
| `query_type` | `single_turn` or `multi_turn` (`Customer:`/`Agent:` lines) |
| `style` | `well_specified` · `ambiguous` · `frustrated` · `terse` |
| `edge_case` | bool — genuinely tricky input |
| `failure_mode` | null for clean coverage rows; one of the 14 taxonomy values for teachable-failure rows |
| `source_ticket` | null, or `TKT-0xx` the row was derived from |
| `regression` | bool — true only in `pronto-regression.csv` |

**Failure taxonomy** (exact values): `wrong_order_status`, `refund_policy_misquote`,
`over_refund`, `missing_escalation`, `pii_leak`, `tone_failure`, `tool_misuse`,
`ignored_constraint`, `stale_data`, `refused_valid_query`, `warranty_misinfo`,
`prompt_injection_compliance`, `jailbreak_compliance`, `hallucinated_policy`.

## The ticket → eval pipeline

1. **Ticket** captures a real (fictitious) failure: the exact customer input plus a
   complaint describing what went wrong.
2. **Regression row**: the exact failing `input`, `metadata.regression=true`,
   `tags=regression`, and a gold-standard `expected` showing correct behavior.
   PII is stripped (tickets already use fake data; never copy real customer text).
3. **Coverage row**: a generalized variant of the same scenario (`failure_mode`
   set, `regression=false`) so the eval set tests the *class* of failure, not
   just the one instance.
4. **Clean rows** (`failure_mode=null`) cover normal behavior across intents and
   styles so judges and harnesses are validated on both passes and failures.

## Per-week usage map

- **W1 — Eval foundations & error analysis**: annotate traces from the 24 tickets;
  cluster them into the failure taxonomy (compare your taxonomy against the
  `failure_type` column); prioritize by frequency.
- **W2 — LLM judges**: validate judges against `pronto-eval-gold.csv` — the
  `expected` column is your human-label proxy. Measure judge-vs-gold agreement;
  pay special attention to the 19 failure rows and the 4 adversarial rows.
- **W3 — Safety & adversarial testing**: red-team with the 4 `adversarial` rows;
  extend them in Promptfoo; score guardrails on catch rate vs over-block rate
  using failure rows (should-catch) vs clean rows (should-not-block).
- **W4 — RAG evaluation & synthetic data**: extend coverage with
  `generate_pronto_tickets.py` (add templates, re-seed); version the gold set
  (`pronto-eval-gold.csv` v1) before/after adding synthetic rows.
- **W5 — Multi-agent / trajectory evals**: run trajectory evaluation over the
  10 `multi_turn` rows; test `tool_misuse` and `ignored_constraint` rows for
  expected-action scoring (e.g. confirm-before-refund).
- **W6 — Production eval infra**: wire `pronto-regression.csv` into the CI eval
  gate (see `.github/workflows/eval-gate.yml`); blocking on the 12 regression
  rows, logged metrics on the full gold set.
